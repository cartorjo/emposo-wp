## Confirmed findings, most severe first

1. **[high] The runbook's vip-config instructions fatal the site at cutover
   step C5.** `docs/install-runbook.md` fact 7 says upload `vip-config/` one
   level ABOVE the WP root but has `wp-config.php` require
   `__DIR__ . '/vip-config/vip-config.php'` — `__DIR__` is the directory
   wp-config.php is in (the web root on this host), so the require points one
   level BELOW. Followed literally at C5, every request fatals until the
   operator notices. `docs/security.md` §2 repeats the contradiction. Fix: one
   consistent location (upload into the WP root next to wp-config.php).

2. **[high] A scaffold re-run after launch silently de-indexes the live
   site.** Every non-dry scaffold ends in `configure_front_page()` →
   `update_option( 'blog_public', 0 )`
   (`class-scaffold-command.php:131,:357-374`), reporting only "41 route
   object(s) present." The runbook's own launch-day order (D1 flip before D4
   verify / D7 define removal) designs in a window where the Scaffold button
   is live on a launched site; the D4 verify subset cannot catch the reset
   (the `blog_public` assertion lives in `verify_options`, which
   routes/content/media skips). It also force-republishes any route an editor
   drafted (`:227`). Fix: scaffold must refuse (or loudly warn and skip the
   option writes) when `blog_public=1`.

3. **[high] Scaffold's slug assertion reads a stale cache and can
   false-abort the documented recovery flow.** The post-write assertion
   (`class-scaffold-command.php:259`) runs `get_post_field( 'post_name' )`
   while `wp_suspend_cache_invalidation( true )` (`:96`) is active, so on the
   update path it can read the pre-write cached slug and raise a fictitious
   "slug became X instead of Y" error — the design comment "nothing here reads
   back what it wrote" (`:86-89`) is false at exactly this line. Bonus
   (unverified-low): the abort cleanup deletes only newly created posts
   (`:264-266`), so an update-path abort leaves a mangled `-2` slug behind.
   Fix: read the slug uncached (direct `$wpdb` or `clean_post_cache` first),
   and unwind the update path on abort.

4. **[medium] `set_time_limit()` is called unguarded outside the try block**
   (`inc/installer.php:198`): on a host that lists it in `disable_functions`
   (shared nginx/FPM hosting — plausible here), every installer step throws an
   uncaught Error before the dispatcher runs. One-line
   `function_exists()` guard.

5. **[medium] Import's editor-protection contract is false for everything
   except records.** The class docblock (`class-import-command.php:8-13`)
   claims per-field hashes make re-runs "safe to run after go-live", but the
   fingerprint logic exists only in `update_fields()` (records). `do_people`,
   `do_terms`, `do_relations`, `do_options`, and the media alt/title refresh
   rewrite unconditionally — a post-launch re-run reverts editor changes in
   those five areas with no `--force` asked. Fix the claim (docblock +
   runbook note) or extend the hashing; at minimum the docs must stop
   promising what only records delivers.

6. **[medium] `verify --media` never checks the 88 AVIF/WebP variant
   files.** `verify_media()` file-exists-checks only `$asset['src']` (the
   JPEG fallback, `class-verify-command.php:457-461`); the variants that
   `picture()` emits into srcsets are unchecked, so a missing/mis-uploaded
   AVIF passes install-day verify and browsers quietly fall back to JPEG,
   breaking the image-budget story. Fix: loop the variants array.

7. **[medium] Identity meta is written after object creation** —
   `_emposo_source_slug` after `wp_insert_post` in `do_people` (`:838→:847`),
   `_emposo_asset_key` after `media_handle_sideload` (`:492→:497`). A request
   killed in that window (FPM timeout on the no-shell host) strands an object
   the re-run cannot find → silent duplicates. Fix: pass identity via
   `meta_input` so creation is atomic.

8. **[low] No `finally` unwind in the installer dispatcher**
   (`inc/installer.php:206-217`): on a Halt or kill, the
   suspend-cache-invalidation unwind and `wp_cache_flush()` that live at the
   commands' happy-path ends never run. Bite requires a persistent object
   cache; production's drop-in is renamed away at cutover per the runbook, so
   low — but a `finally` block is cheap insurance.

## Outcome (same day)

All eight findings plus the actionable tail items were fixed in
`a1c7400..cb30208` and are green in CI. The fix round itself surfaced three
more defects, each fixed and regression-proven: the launch guard's

the guard now keys on created-vs-updated routes, not the option), a latent

pretty URLs at Apache; `wp:bootstrap` now writes the file itself. With all of
it landed, the verdict below is satisfied: **GO.**

## Verdict

**NO-GO as-is; GO after fixes 1–4.** Finding 1 fatals the site mid-cutover if
the runbook is followed literally; findings 2–3 corrupt exactly the
install-day flows (recovery re-runs, post-launch operation) the design leans
on; finding 4 can brick the installer on this class of host. All four are
small, contained changes. Findings 5–8 and the tail items should land with
them but would not individually block an install. Every gate is green and the
probe found runtime behavior matching the docs everywhere except the noted
editor-protection overclaim — the codebase is in strong shape; the defects
cluster in the newest, never-before-reviewed code, which is what the review
was pointed at.
